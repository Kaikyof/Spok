Журнал изменений проекта лежит в двух файлах с одинаковой структурой:

- `CHANGELOG.ru.md` — русский;
- `CHANGELOG.md` — английский.

Формат — [Keep a Changelog 1.1.0](https://keepachangelog.com/ru/1.1.0/). Из этих файлов CI собирает описание GitHub Release (`scripts/release_notes.sh`): для тега `vX.Y.Z` — раздел `[X.Y.Z]`, для dev-тега `vX.Y.Z-dev.N` — раздел `[Unreleased]`.

Режим определи по запросу: **запись** (по умолчанию) или **выпуск версии** («выпусти 0.2.0», «подготовь релиз»).

## Правила для обоих режимов

- **Оба файла меняются всегда вместе.** Те же разделы, те же пункты, в том же порядке. Перевод по смыслу, а не дословно.
- Разделы внутри версии — только эти и только в этом порядке; пустые не пишем:

  | ru | en | что сюда |
  |---|---|---|
  | Добавлено | Added | новые возможности |
  | Изменено | Changed | изменения существующего поведения |
  | Устарело | Deprecated | то, что скоро удалим |
  | Удалено | Removed | удалённые возможности |
  | Исправлено | Fixed | исправленные ошибки |
  | Безопасность | Security | уязвимости |

- Журнал — для людей, которые пользуются приложением, а не для разработчиков. Пункт описывает, что изменилось для пользователя, а не что сделано в коде: «Секреты на Linux без keyring сохраняются в файл с правами 0600», а не «fix: fallback в SecretStore».
- **Не попадает в журнал:** тесты, CI, рефакторинг без видимого эффекта, тулинг, документация, openspec-артефакты, бампы зависимостей без видимого эффекта.
- Один пункт — одно изменение, одна-две строки. Пишется в прошедшем или настоящем времени, без слов «теперь мы».
- Даты — `YYYY-MM-DD`.
- Не трогай уже выпущенные разделы. Исключение — явная просьба пользователя исправить опечатку.

## Режим «запись»

1. Найди изменения ветки: `git log --no-merges --format='%h %s%n%b' origin/develop..HEAD` и `git diff --stat origin/develop...HEAD`. Если пользователь описал изменение сам, бери его описание. Если в ветке есть openspec-change (`openspec/changes/<name>/proposal.md`), возьми смысл оттуда — там написано «зачем».
2. Прочитай оба файла целиком: возможно, часть изменений уже записана. Не дублируй.
3. Отбери изменения, видимые пользователю, и разложи их по разделам. Если видимых нет, скажи об этом и ничего не пиши.
4. Добавь пункты в `## [Unreleased]` обоих файлов. Если раздела-типа ещё нет, создай его на своём месте по порядку из таблицы.
5. Проверь итог: `./scripts/release_notes.sh v0.0.0-dev.0`. Это печать `[Unreleased]` в том виде, в каком он попадёт в релиз.
6. Покажи пользователю добавленные пункты (ru и en). Не коммить, пока не попросят.

## Режим «выпуск версии X.Y.Z»

1. Версию называет пользователь. Если не назвал, предложи по semver исходя из `[Unreleased]` (Removed/несовместимое → major, Added → minor, только Fixed → patch; пока версия `0.x`, несовместимое → minor) и спроси.
2. Проверь, что `[Unreleased]` не пуст в обоих файлах. Если пуст, остановись: выпускать нечего.
3. В обоих файлах:
   - под `## [Unreleased]` вставь `## [X.Y.Z] - <сегодня>` и перенеси туда всё содержимое `[Unreleased]`; сам `[Unreleased]` оставь пустым;
   - обнови ссылки внизу файла:
     ```
     [Unreleased]: https://github.com/Kaikyof/Spok/compare/vX.Y.Z...develop
     [X.Y.Z]: https://github.com/Kaikyof/Spok/compare/v<предыдущая>...vX.Y.Z
     ```
     Для первой версии без предыдущей: `[X.Y.Z]: https://github.com/Kaikyof/Spok/releases/tag/vX.Y.Z`.
4. Подними `version:` в `pubspec.yaml` до `X.Y.Z`, номер сборки после `+` не трогай: в CI его всё равно задаёт `--build-number`.
5. Проверь: `./scripts/release_notes.sh vX.Y.Z` должен напечатать раздел на обоих языках без ошибки.
6. Покажи diff. Тег `vX.Y.Z` ставится после мержа PR, на коммите в целевой ветке. Сам тег не создавай и не пушь без явной просьбы: push тега запускает релизные сборки.
