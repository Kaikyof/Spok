# Часть 0. Суть продукта

### Бизнес

Команда ведёт разработку по строгому процессу: спека → задачи в трекере →
реализация → ревью → сборка → тестирование → архив. Процесс хороший, но
**невидимый**: состояние размазано по Redmine, GitLab, git, файлам репозитория и
мессенджеру. Ни один экран не показывает их вместе.

Чтобы ответить «можно ли отдавать работу тестировщику», человек выполняет 5–10
команд в терминале и сводит ответ в голове. И ошибается, потому что системы
расходятся молча: в трекере задача «готова», а код не влит; галочки проставлены,
а ветка со спеками не доехала.

Проверка на живых данных: при первом запуске приложение нашло **семь
расхождений** и две проблемы окружения, которые человек не видел.

### Техника

Приложение **ничего не хранит и не вычисляет само**. Каждое обновление — полный
пересбор слепка из трёх источников: файлы репозитория спеки, API трекера и
хостинга кода, вывод git. Сервер не нужен: общее состояние уже общее, каждый
работает под своими ключами.

Действия не дублируются: передача, реализация, генерация — это запуск
существующих команд и скриптов спеки. Приложение отвечает за **видимость и
предпросмотр**, спека — за действие.

### Макет

Из этого следуют принципы, которые уже заложены в бордах и должны сохраниться
при любой доработке:

- **состояние важнее действий** — экран отвечает «где мы», кнопки появляются как следствие;
- **факт рядом с ярлыком** — статус трекера и реальное состояние ветки показываются вместе, расхождение выделено;
- **разные по цене действия выглядят по-разному** — посмотреть, изменить локально, написать команде;
- **ничего не уходит наружу без предпросмотра**;
- **команда всегда видна** — рядом с действием строка, которую можно скопировать;
- **цвет не единственный носитель смысла** — состояние читается на монохромном скриншоте;
- **плотность выше красоты** — инструмент открыт весь день рядом с IDE;
- **только реальные статусы** — показываются те, что существуют в трекере спеки;
  приложение не вводит собственных категорий и оценок;
- **тема тёмная** — инструмент живёт рядом с IDE и терминалом.

# Часть 2. Сдвиг: от одной спеки к любой

### Бизнес

Каждая команда WebAnt ведёт свою спеку. Инструмент, который работает только с
одной, — внутренняя утилита одного проекта. Инструмент, который подключается к
любой спеке за минуту, — продукт, который можно раздать всем командам.

Требование: **подключение по git-URL**, без ручной подготовки машины. Человек
вставляет ссылку, приложение клонирует, распознаёт устройство спеки, спрашивает
недостающие ключи — и работает.

### Техника: манифест уже существует

Главный вывод разбора `avelacom-platform`: **придумывать формат описания не
нужно** — метаданные уже лежат внутри спеки.

| Файл | Что даёт |
|---|---|
| `openspec/config.yaml` | имя схемы (`schema: spec-driven-redmine`) |
| `openspec/schemas/<schema>/schema.yaml` | артефакты и **точные имена файлов** (`generates: tasks_backend.md`), список стеков (артефакты `tasks-<stack>`), зависимости (`requires`), `apply.instruction` с именем ветки |
| `openspec/redmine.yaml` | статусы с `id`, `name`, `closing`, `completes_task` и семантика `sync.on_*_status_id` |
| `redmine.yaml` внутри change'а | закэшированные `status_id`/`status_name` по стекам |
| `workspace.yaml` | сервисы, ветки, роли (если есть) |
| `.env.example` | какие ключи нужны этой спеке |

Отсюда: discovery **читает метаданные**, а эвристика по именам файлов остаётся
только запасным путём. Вопрос пользователю «какой статус означает готовность»
отпадает для любой openspec-спеки.

**Версии форматов различаются.** `redmine.yaml` change'а у avelacom помечен
`version: 3`, у avtoto формат другой (там `group.feature_sprint`). Разбор должен
идти **по полю `version`**, а не «как повезёт»: неизвестная версия — явная
ошибка с указанием файла, а не молчаливое пустое значение.

### Что ломается на avelacom сегодня

| Место | Результат |
|---|---|
| корень спеки | распознан (`workspace.yaml` есть) |
| спринты | **0** — в `openspec/doc` лежат `.md`, а код берёт каталоги |
| экран передачи | **вечный лоадер** — нет группы |
| стеки change'а | **пусто** — ищутся `tasks_ios.md`/`tasks_android.md`, а там `tasks_backend.md` |
| статусы | **нет** — читаются `stacks.ios/android.issue_id` |
| MR | пусто — цепочка стартует с группы |
| ключи `.env` | часть не показана: белый список скрывает `REDMINE_PROJECT_ID` и `OPENSPEC_REPO_URL` |
| команды | работают, но ~50 дублей из шести каталогов и нет автокомплита аргументов |
| сессии | работают |

Итог: приложение запускается и показывает пустоту. Не падает — но бесполезно.

### Вердикт по применимости

Ни один экран не исчезает: часть работает полностью, часть — в урезанном виде
с объяснением, чего не хватает.

| Экран | На avelacom | Что нужно доделать |
|---|---|---|
| Сессии + палитра команд | работает почти как есть | дедуп каталогов, `name` из frontmatter, парсер `**Input**` |
| Документы | работает | список артефактов из схемы |
| Окружение | работает | ключи из `.env.example` целиком, а не из белого списка |
| Change'и | частично | стеки из схемы, задачи из `tasks_<stack>.md`, статусы из кэша |
| Расхождения | частично | статусы из `openspec/redmine.yaml` |
| Группа (Спринт) | частично | стратегия `masterDoc` — таблица по мастер-спеке |
| Передача | частично | экран остаётся, шаги деградируют, показывается чеклист требований |
| Код (MR) | выключено | нет `GITLAB_TOKEN` в `.env.example`, нет `roles` — по умолчанию выключено |

### Макет

Нужны **новые борды**, которых нет вовсе:

1. **Мастер подключения проекта** — 4 шага: URL → клонирование с прогрессом →
   результат распознавания → форма ключей.
2. **Селектор проекта в шапке** — сейчас там только спринт; проектов будет много.
3. **Экран результата discovery** — «что распознано» с возможностью поправить:
   тип группировки, стеки, статусы, команды, включённые фичи.
4. **Настройки проекта** — то же, но открывается позже из меню.

И **правки существующих**: шапка получает второй уровень (проект → группа),
пустые состояния экранов перестают быть пустыми (см. часть 5).

# Часть 3. Модель данных: три опциональных уровня

### Бизнес

У разных команд разная глубина процесса. У avtoto: спринт → change → стек →
задачи. У avelacom: мастер-спека → change → задачи (стек один, спринтов нет).
У третьей команды может не быть и мастер-спеки.

Инструмент не должен требовать структуры, которой у команды нет, и не должен
показывать переключатели с одним вариантом.

### Техника

**Уровень 1. Группа вместо спринта.** «Спринт» перестаёт быть сущностью и
становится **стратегией группировки**. Discovery выбирает первую подходящую,
человек может сменить.

| # | Стратегия | Признак | Что становится группой |
|---|---|---|---|
| 1 | `sprintDir` | `openspec/doc/<id>/` с `sprint.yaml` | спринт (ветки, сборки, передача) |
| 2 | `masterDoc` | `openspec/doc/*.md` + ссылка change'а | мастер-спека |
| 3 | `trackerParent` | `group.parent_issue_id` | родительская задача трекера |
| 4 | `trackerVersion` | `fixed_version` задач | версия/майлстоун |
| 5 | `groupMembers` | `group.members` | явный набор change'ей |
| 6 | `none` | ничего из перечисленного | плоский список change'ей |

```dart
class Group {
  final String id;
  final String title;
  final GroupingKind kind;             // sprintDir | masterDoc | trackerParent …
  final Map<String, String> branches;  // пусто — блок «Код» без цели MR
  final Map<String, BuildInfo> builds; // пусто — фича сборок выключена
  final String? docPath;               // мастер-спека для рендера
  final List<String> changeIds;
}
```

### Привязка к уже существующей структуре трекера

**Бизнес.** Сегодня подразумевается, что всё создаётся с нуля: команда пишет
мастер-спеку, потом заводит задачи, и корневая задача рождается вместе с ними.
В жизни бывает иначе: версия или корневая задача **уже существует** — там уже
лежит пул задач, а команда хочет добавить туда новую фичу, спринт или отдельный
change. Заставлять человека создавать дубль корня, а потом переносить задачи
руками — худший из возможных сценариев.

**Техника.** Контракт для этого уже есть в данных, приложение его просто не
использует при создании:

| Поле | Где | Пример |
|---|---|---|
| `group.parent_issue_id` | `redmine.yaml` change'а | у avelacom `63368` — реальная привязка к существующей задаче |
| `group.root_issue_ids.<stack>` | `redmine.yaml` change'а | у avtoto корневые задачи по стекам |
| `fixed_version` | задача в трекере | версия/майлстоун как группа |

Соответственно, приложение должно уметь **выбрать существующий корень** и
передать его в команду создания, а не только принимать то, что она создаст сама.
Источники для выбора: `GET /projects/:id/versions.json` (версии проекта) и
задачи-кандидаты в корни (`GET /issues.json?…`).

**Как это отметить в интерфейсе.** Двумя путями сразу — список как основной,
ручной ввод как запасной:

1. **Чекбокс «Добавить в существующую версию или задачу»** в диалогах создания
   (новый спринт, новый change). Снят — поведение как сейчас, корень создаётся.
   Поставлен — раскрывается выбор.
2. **Селектор из трекера** — подтянутый список версий и корневых задач с
   названиями и номерами. Человек видит «Релиз 3.7 · 12 задач», а не голый id.
3. **Поле URL или номера** — запасной путь, когда версия в другом проекте или
   список слишком длинный: вставляется `https://r.webant.ru/versions/123` либо
   `#63598`, приложение разбирает и показывает, что нашло, для подтверждения.
4. **Выбранный корень виден до запуска** — в предпросмотре команды строкой
   «задачи будут созданы внутри: Релиз 3.7 (#63598)». Ничего не уходит наружу
   без предпросмотра.

После создания привязка сохраняется в `redmine.yaml` change'а, и та же версия
становится доступной **как группа** на главном экране — через стратегии
`trackerVersion` и `trackerParent`. То есть выбор существующего корня и
группировка по нему — это одна и та же сущность, показанная в двух местах.

**Уровень 2. Стеки опциональны.** `ChangeUnit.stacks` может быть пустым.
Правило: **стек = артефакт схемы вида `tasks-*`**, а не любой ключ в
`stacks:` — иначе `root` и `manager` дадут фантомные стеки без задач.
Служебные ключи без файла задач показываются как роли задач change'а, не как стеки.

Когда схемы нет и работает эвристика, имена файлов сопоставляются с найденными id
**по нормализованному сравнению**: `tasks_ios`, `tasks-ios`, `tasksIos`, `ios` —
это один и тот же стек `ios`.

**Уровень 3. WorkUnit.** Общий тип единицы работы: change без стеков имеет один
`WorkUnit`, со стеками — по одному на стек. Все usecases (`FindDivergences`,
`AssessHandoffReadiness`) работают со списком `WorkUnit`.

**Связь change → группа для стратегии `masterDoc`.** У avelacom она явная в двух
местах: в тексте мастер-спеки есть раздел «Набор OpenSpec changes» с перечислением
id, и change'и создаются командой `propose <change> --doc <name>`. Читать надёжнее
**список из документа** (раздел с id в бэктиках или таблица трассировки), а
`group.members` использовать как уточнение.

Сопутствующие правки: `Sprint` удаляется как тип, `state.sprint` → `state.group`;
`Sprint.branchIos/buildIos` → `Map<String, …>`; `enum StackFilter` → `String?`.

### Макет

Таблица главного экрана должна быть спроектирована в **четырёх вариантах**:

| Вариант | Как выглядит |
|---|---|
| Группа + 2 стека | текущий борд 01 (колонки iOS/Android) |
| Группа + 1 стек | одна колонка на всю ширину, **переключатель стеков скрыт** |
| Группа без стеков | одна колонка «Работа», задачи и статус на уровне change'а |
| Без группировки | селектор группы скрыт, заголовок «Change'и», таблица та же |

Плюс: селектор в шапке меняет подпись по типу группировки — «Спринт», «Мастер-спека»,
«Родительская задача», и это надо отрисовать.

# Часть 4. Экраны: бизнес → техника → макет

## 4.1. Подключение проекта (новый)

**Бизнес.** Человек получает ссылку на спеку своей команды и должен начать
работать, не открывая терминал. Ошибки git (нет доступа, занят каталог) должны
объясняться по-человечески, а не кодом.

**Техника.** `SpecProject { slug, title, remoteUrl, ref, localPath, profile,
settings }`, реестр `projects.json` в data-каталоге с атомарной перезаписью.
`GitCloneSource`: `git clone --progress` с прогрессом и отменой, разбор типичных
ошибок (`Permission denied (publickey)`, `Authentication failed`, каталог занят).
Уже клонирован — сверяем `git remote get-url origin` и делаем `pull`.

**Макет.** Мастер из четырёх шагов, все видны сразу:

1. **URL** — поле ввода, кнопка «Подключить», вторая ветка «Указать локальный каталог»;
2. **Клонирование** — прогресс, кнопка «Отменить», состояние ошибки с человеческим текстом;
3. **Распознано** — карточки: тип группировки, стеки, статусы, команды, фичи; у каждой «изменить»;
4. **Ключи** — форма из `.env.example` (см. 4.5).

Если у команды уже есть версия или корневая задача в трекере, её можно указать
здесь же — см. раздел о привязке к существующей структуре в части 3.

## 4.2. Группа (бывший «Спринт»)

**Бизнес.** За пять секунд показать, где работа и что мешает. Это сценарий, ради
которого всё делается.

**Техника.** Список change'ей группы, статусы из кэша `redmine.yaml` change'а
(мгновенно, офлайн) + обновление по API для свежести. Правила расхождений
строятся на семантике `sync.*` из `openspec/redmine.yaml`, а не на русских
строках в коде.

**Макет.** Правки борда 01:

- заголовок и селектор — по стратегии группировки (4 варианта таблицы из части 3);
- **селектор показывает версии и корневые задачи трекера наравне со спринтами**,
  когда группировка идёт по ним: «Релиз 3.7 · 12 задач», а не голый номер;
- **новое состояние: статус из кэша** — нужен визуальный признак «данные из файла,
  трекер не опрошен» (например, приглушённая точка + подпись в подвале таблицы),
  чтобы человек не принял устаревшее за живое;
- пустая группа: объяснение + кнопка «Создать change» (уже есть в приложении, нет в макете);
- фильтр стеков рисуется только при ≥2 стеках.

## 4.3. Change

**Бизнес.** Всё об одной единице работы: что сделано, что мешает, где код, что
обсуждали. Отсюда же запускается реализация — без перехода в терминал.

**Техника.** Список артефактов строится **из схемы** (`artifacts[].generates`), а
не из констант `proposal.md`/`design.md`/`tasks_ios.md`. `requires` из схемы даёт
порядок и подсказку «чего не хватает». Блок «Код»: MR ищется по ветке
`features/<change>` — при наличии `roles` в репозитории стека, иначе во всех
сервисах.

**Макет.** Правки борда 02:

- **артефакты — динамический список** (у avelacom это `test_case.md`,
  `specs/<capability>/spec.md`, `.openspec.yaml`); нужен вид «артефакт объявлен
  схемой, но файла нет» — серая строка с пометкой;
- **полнота артефактов** — индикатор «3 из 5 артефактов заполнены» по `requires`;
- **меню «Ещё действия»** рядом с кнопкой «Реализовать» — команды, применимые
  к change'у по сигнатуре (у avtoto ещё пять). Без него ежедневное «отдать на
  ревью» остаётся спрятанным в палитре;
- **блок «Код» в выключенном виде** — три разных текста по природе нехватки
  (см. 4.8): спека не использует MR · токен не заполнен у меня (с кнопкой
  «Заполнить») · хостинг не отвечает. Даже без токена показываем **ссылку
  «Открыть в GitLab»**, собранную из адреса и имени ветки: API недоступен, но
  сходить руками человек может;
- карточка без стеков — чеклист один, без заголовка стека.

## 4.4. Передача

**Бизнес.** Собрать всё нужное и отдать тестировщику одним действием, видя
заранее, что именно уйдёт людям и что изменится в задачах.

**Техника.** Фичи включаются по факту наличия данных: `sprints` (каталоги с
`sprint.yaml`), `builds` (`builds.yaml`), `handoff` (сборки + роль `handover`),
`mergeRequests` (токен хостинга + сервисы), `chat` (ключи мессенджера или скрипт
получателей), `stacks` (≥2 стека с задачами). Требования фичи «Передача»
проверяются явно:

| Требование | Где ищем | Без него |
|---|---|---|
| `stacks-or-single` | схема / файлы задач | — работает и без стеков |
| `status-semantics` | `openspec/redmine.yaml` → `sync.*` | **блокирует** — нельзя считать готовность |
| `grouping` | стратегия группировки | **блокирует** |
| `builds-file` | `builds.yaml` группы | шаг «Сборки» серый |
| `handover-command` | команда с ролью `handover` | нет кнопки запуска |
| `recipients-script` | `scripts/*handover*recipient*` | шаг «Получатели» скрыт |

Получатели: скрипт спеки печатает секции и участников; поддержать `--format json`
и предпочитать его, парсинг русского текста оставить как fallback.

**Макет.** Правки борда 03:

- шаги должны иметь **три состояния**: активен, выполнен, **недоступен с причиной**
  (сейчас в макете только приглушение);
- у недоступного шага — строка «чего не хватает и где это должно лежать»;
- вариант экрана, где фича недоступна целиком — см. 4.8.

## 4.5. Окружение и форма ключей

**Бизнес.** Половина сбоев начинается здесь. Плюс новое: человек не должен
править `.env` руками в терминале — ключи вводятся в приложении, секреты не
светятся на экране.

**Техника.** Белый список `_criticalEnvKeys` удаляется — поля строятся из
`.env.example` **целиком** (иначе у avelacom скрылись бы `REDMINE_PROJECT_ID` и
`OPENSPEC_REPO_URL`). Подсказка к полю — комментарий над строкой в `.env.example`.
Секреты (`*_TOKEN`, `*_KEY`, `*_SECRET`, `*PASSWORD`) → системное хранилище
(Keychain/libsecret) через `SecretStore`, остальное → реестр проектов.
`EnvMaterializer` пишет `.env` в клон при активации проекта и после сохранения —
файл нужен скриптам спеки и агентным сессиям; при записи проверяется, что `.env`
попадает под `.gitignore`.

**Макет.** Борд 04 переделывается и дополняется:

- **новый борд: форма ключей** — поля с подсказками, маскированные секреты,
  кнопка «Проверить» у каждой группы, состояние «сохранено в Keychain»;
- секции по рабочим местам (спека и её тулчейны), а не один плоский список;
- строка «Проект · url · ветка» в шапке экрана;
- честная пометка, когда секреты лежат в файле, а не в хранилище (нет keyring-демона).

## 4.6. Сессии

**Бизнес.** Часть работы требует суждения и ведётся моделью в диалоге. Из
интерфейса запускается то же, что человек запускал бы в терминале, — с видимым
списком действий и полным логом.

**Техника.** `claude -p … --output-format stream-json --resume <id>` в каталоге
проекта. Команды собираются из источников с приоритетом:
`openspec/schemas/*/commands` (канон) → `.claude/commands/**` →
`.claude/skills/*/SKILL.md` → зеркала (`.codex`, `.cursor`, `.kilocode`,
`.windsurf`), **дедуп по basename**. Дополнительно подхватываются скрипты
`package.json` и цели `Makefile` — у avelacom там `opsx:new`, `openspec:redmine`,
`workspace-init`.

**Разделитель в именах различается**: файл называется `opsx-apply.md`, frontmatter
даёт `name: /opsx-apply`, а документация и apply-инструкция пишут `/opsx:apply`.
Брать надо `name` из frontmatter, иначе имя файла — и не пытаться нормализовать
разделитель самостоятельно. Аргументы — `argument-hint`, иначе парсинг строки `**Input**:` из тела.
Настройки сессии (`model`, `effort`, `permission-mode`, `--resume` id) хранятся
**по проекту**, иначе резюме уйдёт в чужой репозиторий.

**Ввод свободного текста обязателен.** Команда спеки почти никогда не
запускается «как есть»: `/opsx:apply <change>` без словесного уточнения — редкий
случай, обычно к ней дописывают, что именно сделать. Поэтому палитра не заменяет
ввода, а дополняет его: выбранная команда подставляется в поле строкой, дальше
человек продолжает текстом, и всё вместе уходит в `claude -p "<команда> <текст>"`.
Поле работает и без команды — как обычный вопрос агенту.

Параметры запуска (`--model`, `--permission-mode`, `--effort`) редактируются
рядом с полем ввода, а не в настройках: они меняются от задачи к задаче
(разбор — минимальный доступ, реализация — расширенный). Последние значения
запоминаются по проекту и подставляются при следующем запуске.

**Роль ≠ применимость.** Это два разных механизма, и путать их нельзя:

- **роль** (`newSprint`, `newChange`, `apply`, `handover`) решает, какая команда
  получает **выделенную кнопку**; определяется скорингом, правится в настройках;
  нет кандидата — выделенной кнопки нет;
- **применимость** решает, где команда вообще показывается, и **выводится из её
  сигнатуры автоматически**: `[change]` → меню действий карточки change'а,
  `[sprint]`/`[group]` → экран группы, без аргументов → общее меню. Настройка
  для этого не нужна.

Это закрывает вопрос «а если у платформы свои особенные команды». У avtoto их
десять, роли покрывают четыре; остальные шесть — не исключения, а обычная часть
процесса, и пять из них принимают `[change]`:

| Команда | Сигнатура | Где появится |
|---|---|---|
| `/opsx-apply` | `[change]` | карточка change — **выделенная кнопка** (роль) |
| `/opsx-submit` | `[change] [stack]` | меню действий карточки |
| `/opsx-reviewer` | `[change] [stack] [action]` | меню действий карточки |
| `/opsx-spec-review` | `[change]` | меню действий карточки |
| `/opsx-archive` | `[change]` | меню действий карточки |
| `/opsx-sprint` | `[sprint] [action]` | экран группы — кнопка передачи (роль) |
| `/opsx-explore`, `/opsx-redmine-push` | без аргументов | общее меню команд |

Недостающие аргументы (`stack`, `action`) спрашиваются при запуске: известное
подставляется из контекста, остальное выбирается из вариантов сигнатуры.

Краевые случаи: нет `argument-hint` и нет `**Input**` в теле — команда остаётся
только в палитре (нормальный исход, его надо показать); скрипты `Makefile` и
`package.json` сигнатуры не имеют и идут в общее меню.

**Макет.** Правки борда 05:

- **терминал — нижняя панель во всю ширину контента** (над панелью запуска, на
  месте нынешней консоли вывода): вывод последней команды сверху, строка ввода
  с подставленной командой и местом для словесного задания снизу;
  **высота меняется перетаскиванием верхней границы** (свёрнут / обычный /
  развёрнут), выбранная высота запоминается;
- **терминал один**: команда и текст живут в одной строке ввода; отдельных полей
  «для команды» и «для текста» не бывает;
- **команду можно не выбирать** — ввод только текстом уходит агенту как обычный
  вопрос; это отдельное состояние строки ввода;
- **палитра — состояние экрана «Сессии»**: всплывает над строкой ввода по «/»
  и подставляет выбранную команду в неё;
- **строка параметров запуска под полем**: модель · уровень доступа · effort —
  три компактных селектора; значения по проекту;
- **пометка источника команды** в палитре (канон схемы / `.claude` / `Makefile`);
- **следующие шаги после завершения** — кнопки продолжения (включая «создать MR»),
  собранные из правил и факта состояния git; этого в макете нет вовсе;
- индикатор проекта, в котором выполняется сессия;
- вид «команда без описания аргументов» — когда `argument-hint` отсутствует.

## 4.7. Документы

**Бизнес.** Спеки, задачи и тест-кейсы читаются в приложении, а не в редакторе.

**Техника.** Дерево строится из артефактов схемы; рендер markdown уже есть.

**Техника (архив).** Архивные change'и лежат с датой в имени каталога
(`2026-07-31-<change>`): сортировать их по дате из имени, а **id хранить
очищенным** — иначе связь с трекером и группой рвётся.

**Макет.** Борд 06 — добавить вид для мастер-спеки-файла (avelacom: один `.md` без
каталога) и для архивных change'ей с датой в имени.

## 4.8. Диагностика выключенной фичи (новый)

**Бизнес.** Ключевое решение: **не прятать, а объяснять**. Если у спеки нет
сборок или передачи, экран остаётся в навигации, но показывает, чего именно не
хватает и как это включить. Это даёт три вещи: фича не забывается, новая спека
получает инструкцию по внедрению прямо в интерфейсе, отладка «почему пусто»
занимает секунды.

**Техника.**

```dart
enum RequirementScope {
  spec,      // не хватает в самой спеке — правится через процесс команды
  personal,  // не хватает лично мне — правится за полминуты в настройках
  runtime,   // всё настроено, но система не отвечает или отклонила ключ
}

class FeatureRequirement {
  final String id;            // 'builds-file', 'gitlab-token'
  final RequirementScope scope;
  final bool satisfied;
  final String? foundAt;      // где нашли, если нашли
}

class FeatureGate {
  final String featureId;     // 'handoff' | 'builds' | 'mergeRequests' | 'chat'
  final List<FeatureRequirement> requirements;
  bool get available => requirements.every((r) => r.satisfied);
}
```

**Природа нехватки важнее самого факта.** Одна и та же выключенная фича может
означать три разные вещи, и путать их нельзя — иначе разработчик пойдёт править
общий файл спеки там, где ему надо просто ввести свой ключ:

| Природа | Пример | Что показываем | Действие |
|---|---|---|---|
| `spec` — не предусмотрено процессом | `GITLAB_TOKEN` отсутствует в `.env.example` (avelacom) | «эта спека не настроена на работу с MR» | правка спеки: шаблон, агент, инструкция |
| `personal` — не настроено у меня | `GITLAB_TOKEN` есть в `.env.example`, но у меня пустой | «чтобы видеть MR, введите свой токен GitLab» | **кнопка «Заполнить»** ведёт прямо в форму ключей к нужному полю |
| `runtime` — настроено, но не работает | ключ есть, ответ 401 или сеть недоступна | «GitLab отклонил ключ» / «GitLab не отвечает» | «Проверить снова» и «Изменить ключ» |

Случай `personal` — самый частый у нового человека в команде: спека всё
поддерживает, а на его машине ключей ещё нет. Он не должен выглядеть как
недоделанная спека.

`SpecDiscovery` возвращает `Map<String, FeatureGate>`; экран рендерит
`gate.available ? <настоящий экран> : FeatureUnavailableView(gate)`. Тексты
инструкций — `assets/features/<id>.md`, рендерятся существующим `AgentMarkdown`.

**Макет.** Новый борд `FeatureUnavailableView`:

- заголовок фичи и одно предложение «зачем она»;
- **чеклист требований**: выполнено / не выполнено, с путём, где искали;
- три кнопки: «Скопировать шаблон» (YAML-заготовка), «Создать через агента»
  (готовый промпт в сессию), «Открыть инструкцию» (markdown);
- в боковой навигации у выключенного пункта — приглушённая иконка и **счётчик
  невыполненных требований**, а не исчезновение пункта.

# Часть 5. Роли и рабочие места

У инструмента три пользователя с разными вопросами к экрану. Сегодня закрыт
только один — разработчик. **Ролей ровно три: разработчик, менеджер,
тестировщик.** Дизайнер и инженер эксплуатации отдельными рабочими местами не
считаются и в макетах не появляются: дизайнерская работа видна как стек
`tasks_design`, эксплуатация — как обычный change.

| Роль | Главный вопрос | Покрыто |
|---|---|---|
| Разработчик | что у меня в работе, что мешает, какая команда следующая | да |
| **Менеджер** | где работа целиком и что заблокировано | **нет** |
| Тестировщик | что проверять, на какой сборке, что уже закрыто автотестами | нет |

## 5.1. Менеджер

### Бизнес

Менеджер смотрит редко и хочет ответ за пять секунд. Ему не нужны стеки, ветки
и чеклисты — он не будет в них разбираться и не должен. Его вопросы: где работа
целиком и что заблокировано.

Вторая половина роли — **он приносит ТЗ**. Сегодня, чтобы запустить работу по
новой фиче, нужно открыть терминал и знать команды. Правильный сценарий:
менеджер вставляет ТЗ → видит живой прогресс → получает ссылку на MR, которую
скидывает разработчикам. Ни одной команды руками.

### Техника

Новых источников данных не требуется — только другая выборка и другая подача:

- **сводка вместо таблицы**: по каждой группе одна строка состояния (готово N из
  M, блокеров K) — считается из тех же `WorkUnit`, что и таблица разработчика;
- **никаких вычисляемых псевдостатусов.** Показываются только статусы, реально
  существующие в трекере этой спеки, и факты из файлов (задача не закрыта, ветка
  не влита, сборка не записана). Приложение не изобретает собственных категорий
  вроде «застряло» или «долго висит» — ни для менеджера, ни для разработчика;
- **«кем заблокировано»** — исполнитель задачи-блокера из трекера;
- **запуск из ТЗ** — существующий диалог создания, но без технических полей:
  имя генерируется из текста, стек не спрашивается;
- **следующие шаги после сессии** — те же кнопки продолжения, но менеджеру
  показывается только одна, значимая для него: «Отдать разработчикам» (создание
  MR через команду спеки) и затем ссылка на созданный MR.

Роль берётся из окружения как предустановка (ADR 0002): она решает, какой экран
открыть первым, но не запирает человека — лид может смотреть оба среза.

### Макет

Отдельный сокращённый экран, а не фильтр над существующим:

- **«Что происходит»** — карточки групп: название, одна строка состояния,
  индикатор блокеров; без колонок по стекам;
- **«Что мешает»** — список блокеров человеческим языком с именем того, кто
  держит;
- **никаких придуманных категорий** — на экране только реальные статусы трекера
  и факты из файлов;
- **«Новая фича из ТЗ»** — крупная кнопка, ведущая в упрощённый диалог;
- **прогресс запущенной работы** — без лога и списка инструментов: заголовок,
  живая строка «что делает агент», кнопка «Отдать разработчикам» по завершении,
  затем ссылка на MR с кнопкой «Скопировать».

Чего на этом экране нет: стеков, веток, чеклистов, панели запуска, окружения.

## 5.2. Тестировщик

### Бизнес

Тестировщик — третий пользователь, тоже не покрыт. Его вопросы:
какие задачи назначены и на какой сборке проверять; где взять сборку; что
проверять руками, а что закрыто автотестами; какие расхождения осознанные; куда
записать результат.

Решение: **не отдельная сборка приложения**, а состав экранов по доступным
источникам. Отдельный продукт дублировал бы весь каркас, а контекст спеки ему
всё равно нужен.

### Техника

QA-репозиторий — это **сервис внутри `workspace.yaml` спеки** (`roles: qa`), а не
отдельная платформа. Отсюда:

- набор экранов определяется тем, что фактически склонировано и настроено;
- роль из окружения — только предустановка первого экрана, не режим;
- сессия знает свой рабочий каталог: `/qa-*` выполняются в QA-репозитории,
  `/opsx-*` — в спеке; палитра собирается из обоих с пометкой принадлежности;
- окружение составное: у тулчейна свои ключи (`ALLURE_*`, `OPENSPEC_REPO`);
- связь кейс ↔ change берётся из `spec_sources` во frontmatter кейса;
- покрытие показывается и без локального клона — прогоны живут в Allure;
- готовность не пересчитывается: вызывается `bin/change-readiness.mjs` тулчейна.

### Макет

- **новый раздел «Тестирование»** в навигации, появляющийся при наличии источника:
  список кейсов, тип (UI / API / E2E), `automation_status`, связь со спекой;
- **блок покрытия в карточке change'а** — «5 кейсов, 3 автоматизированы»;
- переключатель рабочего места рядом с селектором проекта;
- вид навигации, где раздела нет вовсе (источник не подключён) — чтобы дизайн не
  ломался при разном составе пунктов.

# Часть 6. Контракты данных для новой спеки

Это то, что приложение ищет, и одновременно инструкция для команды, желающей
включить у себя фичу.

### Сборки — `builds.yaml` в каталоге группы

```yaml
<stack>:                       # id стека из схемы: ios | android | backend …
  builds:
    - version_name: "1.4.0"    # обязательно
      version_code: 152        # опционально → показываем «1.4.0(152)»
      channel: "TestFlight"    # опционально: чем собрано / куда выложено
      published_at: 2026-08-20T14:03:00Z
      url: https://…           # опционально: ссылка на артефакт
```

Первая запись — последняя сборка.

### Ветки группы — `sprint.yaml` (или `group.yaml`)

```yaml
branches:
  <stack>:
    name: sprint/2026-08-pin-auth
delivery: batch | per-change
```

Нужно для блока «Код» (цель MR) и проверки «влит ли change в ветку сдачи».

### Получатели — скрипт спеки

Исполняемый файл по маске `scripts/*handover*recipient*`, печатающий секции:

```
Тестировщики:
- @username — Имя Фамилия (Redmine 328)
Менеджеры:
- @username2 — Имя Фамилия (Redmine 415)
```

Улучшение: поддержать `--format json` и предпочитать его.

### Команда передачи

Любая команда агента с ролью `handover` — эвристика или ручная пометка.
Аргументы подставляются по `argument-hint` / `**Input**`.

# Часть 7. План работ

### Бизнес-порядок

Сначала — чтобы приложение вообще открывалось на чужой спеке (этапы 0–3), потом —

# Часть 8. Открытые вопросы и ограничения

- **Трекер и хостинг прибиты.** Redmine и GitLab зашиты в `redmine_api`,
  `gitlab_api`, `redmineStatus`, `RedmineProblem`, `RedmineIssueLink` и ~15 строк
  локализации. Абстракция делается только когда появится команда не на Redmine.
- **Не-openspec спека** поедет только на эвристике — результат обязательно
  показываем и даём править.
- **Разрешения агента.** Команды спеки вне allow-списка требуют режима с
  автоматическим разрешением. Альтернатива — правило в настройках спеки.
- **История сессий** не сохраняется между запусками.
- **Интерактивные запросы разрешений** внутри сессии требуют
  `--permission-prompt-tool`.
- **Распространение.** Сборка не подписана: у коллег первый запуск задерживает
  Gatekeeper. Лечится Developer ID и нотаризацией.
- **Discovery полного дерева дорог** — выполняется при подключении, по кнопке и
  при смене `HEAD`, а не при каждом старте.
- **Расширение схемы avtoto.** Спринты, сборки и передача — де-факто расширение
  openspec-схемы, живущее вне схемы. Правильнее описать их в самой схеме avtoto;
  тогда discovery станет однородным. Это работа на стороне спеки, не консоли.
- **Интерфейс только русский, тема тёмная.**
