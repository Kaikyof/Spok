## Короткая версия

**Совместимость с оригинальным OpenSpec делается без переписывания.** Для
Spok это вырожденный случай уже поддерживаемой модели: схема есть, но лежит не
в проекте; стеков, трекера, группировки и `workspace.yaml` нет. Ломается то,
что считалось обязательным: схема только в `openspec/schemas/`, задачи только
по стекам `tasks-<stack>`, статус только из трекера.

**Open Source и потребности команды не противоречат друг другу, если провести
одну границу.** Всё, чего нет в оригинальном OpenSpec, — трекер, хостинг кода,
мессенджер, спринты, сборки, передача, `workspace.yaml` — становится
**расширениями**, которые включаются по уликам в самой спеке. У спеки нет
`openspec/redmine.yaml` и ключей `REDMINE_*` — расширения трекера нет ни в
навигации, ни на карточке, ни в разборе. Есть — работает как сейчас, со всеми
чеклистами требований. Один код, одна сборка, а что видит человек — решает
его спека.

Это уточняет принцип «не прятать, а объяснять» из сводного документа (4.8):
**объяснять то, что спека обещает, и не показывать то, чего она не обещает.**
Инструкция «как включить у себя передачу» никуда не исчезает — переезжает
с главного экрана в настройки проекта, раздел «Расширения».

Работа сводится к пяти вещам:

1. **Схема** — встроенная `spec-driven` из пакета upstream (копия в assets),
   разрешение по цепочке upstream (change → конфиг → умолчание), `apply.tracks`.
2. **Единица работы без стеков и без трекера** — один `tasks.md` и парсер
   чекбоксов, совместимый с upstream.
3. **Стадия работы** из файлов (какие артефакты написаны, сколько задач
   закрыто, в архиве ли) — статус, который есть у любой спеки; трекер — слой
   поверх.
4. **Команды upstream** — имя вызова из пути, дедуп скилла и команды,
   применимость без `argument-hint`.
5. **Ядро и расширения** — контракт расширения, активация по уликам, правило
   «скрыть или объяснить», разнос по пакетам с проверкой в CI, английский
   интерфейс по умолчанию.

Минимум для «открывается на проекте после `openspec init`» — этапы 0–3.
Минимум для выпуска в Open Source — плюс этапы 4 и 6.

## 1. Как устроен оригинальный OpenSpec

В терминах, которыми Spok уже пользуется. Колонка «recmeet» — из
`finding-recmeet-spec.md`, для полноты картины.

| | avtoto | avelacom | recmeet | **upstream OpenSpec** |
|---|---|---|---|---|
| Где схема | `openspec/schemas/<name>/` | там же | там же | **в npm-пакете** (`schemas/spec-driven/`), в проекте только если форкнута; ещё `~/.local/share/openspec/schemas/` |
| Имя схемы | `config.yaml → schema` | там же | там же | цепочка: `--schema` → `.openspec.yaml` change'а → `config.yaml` → **`spec-driven` по умолчанию**; `config.yaml` может отсутствовать |
| Артефакты | proposal, specs, design, tasks-ios, tasks-android … | proposal, specs, tasks-backend, test_case … | proposal, system_design, `<stack>/tasks.md` | `proposal` → `specs/**/*.md` → `design` → **`tasks` (один файл)** |
| Кто отслеживает задачи | артефакты `tasks-<stack>` | там же | там же | **`apply.tracks: tasks.md`** в схеме |
| Формат задачи | `- [ ] 1.1 текст` | там же | там же | любой маркер списка (`-`, `*`, `+`, `1.`), вложенность, `[x]`/`[X]` — сделано, любой другой маркер (`[~]`, `[]`) — **не сделано**, номер необязателен |
| Метаданные change'а | `redmine.yaml` (v3/v4) | `redmine.yaml` v3 | v2 у группы, v4 у change'а | **`.openspec.yaml`**: `schema`, `created`, `goal`, `skip_specs`, `retire_capabilities`, `affected_areas`, `initiative` |
| Трекер | Redmine, `openspec/redmine.yaml` | Redmine | Redmine | **нет** — статус выводится из файлов: `no-tasks · in-progress · complete` (`openspec list`), готовность артефактов (`openspec status`) |
| Группировка | каталог спринта | мастер-спека файлом | каталог-группа в `changes/` | **нет**; вложенные каталоги в `changes/` upstream **явно не поддерживает** (диагностика `nested-change.ts`, issue #1846) |
| Ветка change'а | из `apply.instruction` | там же | там же | **не объявлена** — upstream веток не диктует |
| Архив | `changes/archive/YYYY-MM-DD-<id>/` | там же | там же | **то же самое** |
| Спецификации | `openspec/specs/**` есть, Spok не показывает | — | — | `openspec/specs/<capability>/spec.md` — **источник правды**, дельты в `changes/<id>/specs/**` (ADDED/MODIFIED/REMOVED) |
| Команды агента | `.claude/commands/opsx-*.md`, `name: /opsx-apply` | + `package.json`, `Makefile` | — | `.claude/commands/opsx/<id>.md` (`name: OPSX: Propose`, вызов **`/opsx:propose` из пути**) и `.claude/skills/openspec-<skill>/SKILL.md` (`name: openspec-propose`), без `argument-hint`; зеркала для 30+ инструментов |
| Набор команд | opsx-apply, submit, reviewer, sprint, doc … | opsx:new, propose … | — | core: `explore · propose · apply · update · sync · archive`; expanded: `new · continue · ff · verify · bulk-archive · onboard` |
| Окружение | `.env.example`, `workspace.yaml`, сервисы | там же | там же | **ничего**: `openspec/` лежит внутри репозитория кода, ключей и сервисов нет |
| CLI | — | — | — | `openspec list/status/validate/show/schemas … --json` |
| Хранилища (beta) | — | — | — | `config.yaml → store: <id>` — change'и живут в другом репозитории, зарегистрированном на машине |

Главный вывод: **новых сущностей нет**. Всё, что есть у upstream, в модели
Spok либо уже описано (схема, артефакты, архив, команды), либо является
«отсутствием» того, что Spok уже умеет объяснять (трекер, группы, стеки,
сервисы). Новое только одно — понятие **стадии работы без трекера**.

## 3. Различия и как их адаптировать

Каждое различие с upstream — и что с ним делать. Колонка «где» говорит, в
ядро это уходит или в расширение (раздел 4): ядро — то, что есть у любого
проекта на OpenSpec; расширение — то, что есть только у спек с трекером,
хостингом, спринтами.

| # | Различие | Как адаптировать | Где |
|---|---|---|---|
| 1 | Схема не в проекте, а в пакете upstream; может отсутствовать `config.yaml` | Копия встроенной `spec-driven` в `assets/openspec/schemas/` с версией upstream в комментарии. Разрешение как у upstream: `.openspec.yaml` change'а → `config.yaml` → `spec-driven`. Источники: проект → `~/.local/share/openspec/schemas/` → встроенная. Когда найден CLI `openspec`, схема берётся из `openspec schema which --json`, копия — запасной путь | ядро |
| 2 | Схема может быть своей у каждого change'а | `SpecSchema` хранится по change'у; экран распознавания показывает схему по умолчанию и «у N change'ей своя» | ядро |
| 3 | Один `tasks.md` вместо `tasks-<stack>` | Файл задач — из `apply.tracks` схемы. Стеки остаются артефактами `tasks-<stack>`; нет стеков, но есть `tracks` — один «стек работы» без условия на трекер. Это и есть `WorkUnit` из части 3 сводного документа, без нового типа | ядро |
| 4 | Парсер чекбоксов upstream мягче | Перенести правила `task-progress.ts`: любой маркер списка, отступ, `[x]`/`[X]` — сделано, прочее — нет, ссылки `- [x](…)` — не задачи, номер необязателен (без него — порядковый) | ядро |
| 5 | Нет трекера — нет статуса | `WorkStage`: `planning(next)` · `readyToApply` · `inProgress` · `done` · `archived`, считается по артефактам в порядке `requires`, чекбоксам файла `tracks` и архиву. Есть у любой спеки, в том числе у avtoto — там стадия становится «фактом» рядом с ярлыком трекера | ядро |
| 6 | Статус трекера — наш слой поверх | `StackState.redmineStatus` → `trackerStatus`, `RedmineProblem` → `TrackerProblem` с новым значением `notDeclared`; цвет точки — по стадии, имя статуса трекера рядом. Расхождения и передача как требовали семантику статусов, так и требуют | расширение `tracker` |
| 7 | Ветка change'а не объявлена | `branchTemplate` nullable: нет `checkout -B … <change…>` в `apply.instruction` — ветки нет; дерево документов её не показывает, блок «Код» (если активен) объясняет: «спека не объявляет имя ветки» | ядро + `code` |
| 8 | `.openspec.yaml` вместо `redmine.yaml` | Читается в `ChangeUnit`: `schema`, `created`, `goal`, `skip_specs`. `skip_specs` — состояние артефакта «пропущен по `.openspec.yaml`», не «не написан». `redmine.yaml` change'а (v3/v4) остаётся кэшем статусов расширения трекера | ядро / `tracker` |
| 9 | Артефакт-маска `specs/**/*.md` | Существует — хотя бы один файл по маске; в карточке считается в «N из M»; в документах — раскрытый список дельт с пометкой ADDED/MODIFIED/REMOVED по заголовкам | ядро |
| 10 | `openspec/specs/**` — источник правды | Узел «Спецификации» в дереве документов с вложенностью по каталогам | ядро |
| 11 | Нет заголовка H1 в `proposal.md` | H1 → `# Proposal: …` без префикса → id. «Очеловечивание» id не делаем | ядро |
| 12 | Команды: `name: OPSX: Propose`, вызов из пути | Вызов для `commands/<ns>/<id>.md` — `/<ns>:<id>`, для `commands/<id>.md` — `/<id>`. `name` из frontmatter — только если похож на вызов (начинается с `/` или без пробелов и заглавных); это сохраняет avtoto (`name: /opsx-apply`) | ядро |
| 13 | Скилл и команда об одном | Скилл склеивается с командой, если его описание называет её фразой `"opsx <id>"` (upstream пишет её в каждый скилл); без пары скилл остаётся командой — `/openspec-propose` тоже валидный вызов | ядро |
| 14 | Нет `argument-hint` | Строка вызова в `**Input**` даёт слоты (как сейчас); проза без строки вызова — `paletteOnly`, а не угадывание по слову «change». Известные роли дают применимость: `newChange` → общее меню, `apply`/`archive` → карточка | ядро |
| 15 | Завершение change'а — архивирование, а не передача | `CommandRole.archive`; следующие шаги после сессии — по стадии: `done` → архивировать, `planning` → продолжить, `readyToApply` → реализовать. Плашка «следующий шаг» в группе — по стадии, когда стеков нет | ядро |
| 16 | Нет `.env.example`, `workspace.yaml`, внешних систем | Список систем на «Окружении» — из ключей `.env.example` (`REDMINE_URL` → Redmine и т. д.), а не зашит. Нет ключей — строка «проект не объявляет ключей»; нет `workspace.yaml` — раздела репозиториев нет вовсе | ядро / `workspace` |
| 17 | `openspec/` внутри репозитория кода | Терминология ядра — «проект», не «спека/платформа»; `git pull --ff-only` при каждом обновлении — только при чистом дереве или по настройке проекта | ядро |
| 18 | CLI `openspec` с `--json` | Необязательный источник: `validate --all --json` (валидация), `status --change --json` (готовность артефактов с правилами `skip_specs`), `schema which --json`. Гейт `runtime`; без бинаря ничего не меняется. Расхождение «наш счёт задач ≠ `completedTasks`» показывать — это сигнал, что парсер отстал | ядро (по желанию) |
| 19 | Хранилища `store:` | Распознать указатель, объяснить: «change'и живут в хранилище `<id>` — откройте его каталог». Не поддерживаем | ядро |

## 4. Open Source: ядро и расширения

### 4.1. Постановка

Команда WebAnt работает с трекером, хостингом кода, мессенджером, спринтами и
передачей — этого нет в оригинальном OpenSpec, и большинству его
пользователей это не нужно. Выпустить Spok в открытый доступ «как есть»
значит показать им навигацию с «Передачей», счётчики невыполненных требований
и разбор спеки со строкой «статусы трекера не распознаны». Выпустить
обрезанную копию значит поддерживать два приложения.

Нужно одно приложение, в котором **командное отделено от общего на уровне
кода**, а **что показывать — решает сама спека**.

### 4.2. Три слоя

```
┌─────────────────────────────────────────────────────────────────────┐
│ приложение (lib/)                                                   │
│   сборка, навигация, регистрация расширений, тема, локали          │
├─────────────────────────────────────────────────────────────────────┤
│ расширения (packages/spok_ext_*)                                    │
│   tracker-redmine · code-gitlab · chat-mattermost · workspace ·     │
│   sprints (спринты, сборки, передача, получатели)                    │
├─────────────────────────────────────────────────────────────────────┤
│ ядро (packages/spok_core)                                           │
│   файлы openspec: схема, change'и, артефакты, задачи, стадия,       │
│   архив, спецификации, команды, сессии, ключи .env, git проекта,    │
│   реестр проектов, клон, секреты, состояния данных                  │
└─────────────────────────────────────────────────────────────────────┘
```

Правило зависимостей: ядро не знает о расширениях; расширения зависят от
ядра; приложение знает обо всех. Слово «Redmine» в ядре — ошибка сборки, а
не замечание на ревью (проверка в CI, см. 4.6).

Что именно куда:

| Сегодня в коде | Слой | Примечание |
|---|---|---|
| схема, артефакты, `apply.tracks`, стеки `tasks-<stack>` | ядро | стеки — из схемы, значит общее: кастомная схема любой команды может их объявить |
| change'и, задачи, `WorkStage`, архив, `.openspec.yaml` | ядро | |
| документы, спецификации `openspec/specs/**` | ядро | |
| команды: схема, `.claude`, зеркала, `package.json`, `Makefile`; роли | ядро | |
| сессии, терминал, палитра, панель запуска | ядро | |
| ключи `.env.example`/`.env`, `SecretStore`, `EnvMaterializer` | ядро | ключи — общий механизм; какие системы за ними стоят — расширения |
| реестр проектов, клон, «Что распознано», состояния данных | ядро | |
| группировка `none` | ядро | плоский список — единственная стратегия, которая есть у всех |
| `openspec/redmine.yaml`, `redmine.yaml` change'а, `RedmineApi`, статусы, комментарии, ссылки на задачи, расхождения по статусу | **tracker-redmine** | порт `Tracker` в ядре, адаптер — в расширении |
| `GitLabApi`, MR, блок «Код», ссылка на ветку | **code-gitlab** | порт `CodeHosting` |
| `MATTERMOST_*`, предпросмотр сообщения | **chat-mattermost** | |
| `workspace.yaml`, сервисы, роли машины `*_ROLE`, репозитории на «Окружении» | **workspace** | сервисы нужны `code-gitlab` — зависимость расширения от расширения допустима, ядро в ней не участвует |
| `sprint.yaml`, `builds.yaml`, мастер-спеки `openspec/doc/*.md`, передача, готовность, получатели, `handover` | **sprints** | зависит от `tracker` (семантика статусов) и `workspace` |

Расширения `tracker-redmine`, `code-gitlab`, `chat-mattermost` — не
«командные», а обычные интеграции: Redmine и GitLab стоят у многих. Они могут
и должны быть в открытом репозитории. По-настоящему командное — соглашения
`spec-driven-redmine` (`redmine.yaml` v3/v4, `sprint.yaml`, `builds.yaml`,
скрипт получателей) — живёт в `sprints` и в адаптере формата у `tracker`;
это тоже можно открыть, а можно держать в отдельном пакете вне публичного
репозитория. Архитектура одинаково выдерживает оба варианта.

### 4.3. Контракт расширения

```dart
/// Расширение — то, чего нет в оригинальном OpenSpec. Включается по уликам
/// в спеке; нет улик — расширения нет нигде, кроме настроек проекта.
abstract class SpecExtension {
  String get id;                              // 'tracker-redmine'
  List<String> get dependsOn;                 // ['workspace']

  /// Улики: файлы и ключи, по которым спека объявляет, что пользуется этим.
  /// `openspec/redmine.yaml` или `REDMINE_URL` в `.env.example` — трекер есть.
  ExtensionEvidence detect(ProjectFiles files);

  /// Требования поверх улик — то, что сегодня `FeatureGate`: ключ заполнен
  /// у меня (`personal`), система отвечает (`runtime`), файл группы есть
  /// (`spec`, необязательное). Чеклист показывается как сейчас.
  FeatureGate gate(ProjectFiles files, EnvReport env);

  /// Данные расширения в слепке. Читаются параллельно с ядром; отказ
  /// расширения — состояние «недоступно с причиной», а не падение слепка.
  Future<ExtensionData> load(ProjectFiles files, ProjectCore core);

  /// Вклады в интерфейс — всё, что расширение добавляет к экранам ядра.
  List<NavItem> navItems(ExtensionData data);                 // «Передача»
  List<ChangeCardBlock> changeCardBlocks(ChangeUnit change);  // «Код», комментарии
  List<GroupColumn> groupColumns();                           // статус трекера, сборки
  List<GroupingStrategy> groupings();                         // sprintDir, masterDoc
  List<RecognizedItem> recognition(ProjectFiles files);       // «статусы: 8»
  List<EnvSystem> envSystems(ProjectFiles files);             // Redmine
  List<DivergenceRule> divergenceRules();                     // ярлык против факта
  List<CommandRole> commandRoles();                           // handover
}
```

Ядро держит **порты**, расширения — **адаптеры**:

```dart
abstract class Tracker {                 // порт в ядре
  String get name;                       // «Redmine» — в тексты вместо зашитого
  Uri? issueUrl(int id);
  Future<Map<int, String>> statuses(List<int> ids);
  Future<List<IssueComment>> comments(int id);
  Future<int> ping();
}
abstract class CodeHosting { … }         // MR, ветка, ping
abstract class Chat { … }                // предпросмотр, отправка
```

`ConsoleSnapshot` получает `Map<String, ExtensionData>` вместо полей
`redmineProblem`, `redmineBaseUrl`; `ProjectProfile.features` уходит в
расширения (каждое несёт свой `FeatureGate`). `SpecFeature` как enum
исчезает — на его месте id расширений.

### 4.4. Правило: скрыть или объяснить

| Улики в спеке | Требования | Что видит человек |
|---|---|---|
| нет | — | **ничего**: ни пункта навигации, ни блока, ни строки в разборе, ни счётчика. Расширение видно только в «Настройки проекта → Расширения»: «не активно — спека не объявляет `openspec/redmine.yaml` и ключей `REDMINE_*`», с инструкцией и шаблоном |
| есть | выполнены | работает как сейчас |
| есть | не выполнены `personal` / `runtime` | как сейчас: экран остаётся, `FeatureUnavailableView` с чеклистом, поле ключа, «Проверить снова» |
| есть | не выполнены необязательные `spec` (`builds.yaml`) | как сейчас: шаг гаснет с объяснением |

Отличие от сегодняшнего — только первая строка. Сейчас «нет улик» и «есть
улики, но не настроено у меня» показываются одинаково: пунктом навигации со
счётчиком и экраном-объяснением. Для avelacom это было правильно (там нет
`GITLAB_TOKEN` в примере, и человек должен узнать, что спека не работает с
MR). Для проекта на оригинальном OpenSpec это шум: там не «не хватает», там
«не предусмотрено».

Это правка принципа 4.8 сводного документа, и её надо принять осознанно:
**объяснять то, что спека обещает, и не показывать то, чего она не обещает.**
Три кнопки из борда 12 («Скопировать шаблон», «Создать через агента»,
«Открыть инструкцию») переезжают в раздел «Расширения» настроек проекта
(борд 13) — там им и место: включение фичи в спеке — действие настройки,
а не ежедневной работы.

Краевые случаи:

- **avelacom** после правила: трекер активен (есть `openspec/redmine.yaml`),
  хостинг кода — есть `workspace.yaml`, но нет `GITLAB_*` в примере. Улика
  сервисов есть, ключей нет → расширение `code` активно, требование «ключ
  объявлен в спеке» не выполнено, природа `spec` → блок «Код» показывается с
  объяснением, как сегодня. Поведение не меняется.
- **avtoto** — все расширения активны, ничего не меняется.
- **upstream-проект** — ни одного активного расширения: навигация «Change'и ·
  Сессии · Документы», разбор из четырёх строк. Экрана «Окружение» нет:
  ни ключей, ни репозиториев, ни систем у него не объявлено (см. 4.5).
- **Человек хочет включить у себя передачу** — идёт в настройки проекта,
  видит список расширений с их уликами, копирует шаблон или запускает агента.

### 4.5. Где расширения врезаются в интерфейс

| Место | Сейчас | С расширениями |
|---|---|---|
| Навигация (`shell.dart`) | список зашит, у пункта — гейт по `SpecFeature` | ядро даёт свои пункты; каждое активное расширение — свои; счётчик — только у активного с невыполненными требованиями |
| Таблица группы | колонки по стекам со статусом трекера | колонка стадии — ядро; статус трекера, сборки — колонки расширений; варианты таблицы по стекам остаются |
| Карточка change'а | спека, чеклисты, артефакты, зависимости, «Код», комментарии | ядро: спека, чеклисты, артефакты, зависимости, стадия; блоки расширений после них в объявленном порядке |
| «Что распознано» | шесть строк, две про трекер и сервисы | строки ядра (схема, группировка, стеки, команды) + по строке от активного расширения; «не распознано» — только когда улики есть, а разбор не удался |
| Окружение | ключи, репозитории, три системы, ветка репозитория спеки | разделы по уликам: ключи — ядро, при `.env.example`; репозитории — `workspace`; системы — по расширению на систему. **Пункт навигации есть только при активном разделе**: нет `.env.example` и `workspace.yaml` — нет и экрана. Ветка и отставание репозитория спеки переезжают в шапку, к чипу проекта, — иначе экран держался бы в навигации ради одной строки. Требования `personal` без `.env.example` не возникают, так что переходов «Заполнить ключи» на скрытый экран не будет — закрепить тестом |
| Передача | экран с гейтом | целиком в `sprints`, появляется только при уликах |
| Сессии | роли `apply · newChange · newGroup · handover` | роли ядра `apply · newChange · archive`; `newGroup`, `handover` — вклад `sprints` |
| Настройки проекта | нет (очередь 3 `design-plan.md`) | раздел «Расширения»: активно / не активно, улики, требования, шаблон, агент |
| Локализация | один `app_ru.arb`, 31 строка с Redmine/GitLab/Mattermost | у каждого пакета свой `l10n` (gen-l10n это умеет); строки ядра говорят «трекер», имя подставляет расширение |

### 4.6. Пакеты и проверка границы

```
spok/
  packages/
    spok_core/            domain + data ядра, свои тесты и l10n
    spok_ext_tracker_redmine/
    spok_ext_code_gitlab/
    spok_ext_chat_mattermost/
    spok_ext_workspace/
    spok_ext_sprints/
  lib/                    приложение: регистрация расширений, shell, тема
  test/                   сквозные тесты на трёх фикстурах
```

Проверка границы в CI — три вещи, и все дешёвые:

1. `flutter analyze` и `flutter test` **отдельно в `packages/spok_core`** —
   пакет обязан собираться без расширений.
2. Тест на импорты: ни один файл `spok_core` не импортирует `spok_ext_*`
   и не содержит слов `redmine`, `gitlab`, `mattermost` (кроме тестовых
   фикстур). Простой скрипт в `tool/`, прогоняется в `linux.yml`.
3. Виджет-тест «upstream-фикстура»: дерево навигации содержит ровно три
   пункта (Change'и · Сессии · Документы), текст экранов не содержит имён
   систем.

Одна сборка для всех. Если понадобится «облегчённая» сборка без командных
расширений — `--dart-define=SPOK_EXTENSIONS=core` в точке регистрации, и
tree-shaking уберёт лишнее. Это не первоочередное: неактивное расширение
и так невидимо.

### 4.7. Что ещё нужно для открытого репозитория

Не архитектура, но без этого выкладывать нельзя:

- **Английская локаль по умолчанию**, русская — по системной локали.
  Сегодня `app_ru.arb` — единственный; строк 400+, это отдельная работа
  (M), её можно вести параллельно этапам.
- **Следы команды**: `AVTOTO_PLATFORM_DIR`, типовые пути `~/avtoto-platform`
  в `locate()`, `PlatformConsole` как имя каталога — оставить только
  миграцией из старого каталога.
- **Лицензия** — MIT, как у upstream; `LICENSE` и заголовок в README.
- **README на английском** с таблицей «что читается откуда» и разделом
  «Extensions: what your spec needs to declare».
- **Подпись сборки** — уже в открытых вопросах сводного документа (часть 8);
  для широкого распространения без неё не обойтись.
- **Название и каналы** — не техника, но решать до публикации.

## 5. Целевое поведение

### На проекте после `openspec init` (core-профиль, Claude Code)

1. Подключение по пути или URL → «Что распознано»: *схема `spec-driven`
   (встроенная upstream), группировка — нет, стеки — нет, команды — 6*.
   Про трекер, сервисы и статусы — ни слова. «Не распознано» — пусто.
2. Навигация: Change'и · Сессии · Документы. «Окружения» нет: проект не
   объявляет ни ключей, ни репозиториев, ни внешних систем.
3. Список change'ей со **стадией** и прогрессом: «планирование · следующий:
   design», «готов к реализации», «в работе 3/7», «сделано 7/7 —
   архивировать», «архив 12.09».
4. Карточка: спека, артефакты «3 из 4» с учётом `specs/**` и `skip_specs`,
   чеклист задач, «Реализовать» (`/opsx:apply`), «Ещё» (`/opsx:update`,
   `/opsx:verify`, `/opsx:archive`). Блока «Код» нет.
5. Документы: «Спецификации» (`openspec/specs/**`), у change'а —
   `proposal.md · specs/… · design.md · tasks.md`, архив с датой.
6. Сессии: палитра без дублей, `/opsx:propose <описание>` и
   `/opsx:apply [change]` уходят в `claude -p`; после завершения — следующие
   шаги по стадии.
7. Ветка репозитория проекта и отставание от удалённой — в шапке, у чипа
   проекта, рядом со свежестью данных.
8. Настройки проекта → Расширения: пять неактивных, у каждого — что добавить
   в спеку, чтобы включить.

### На avtoto и avelacom

Ничего не меняется, кроме появления стадии рядом со статусом трекера и
переезда кнопок «Скопировать шаблон / Создать через агента» из экрана
выключенной фичи в настройки проекта. Тесты `test/` и оба смоука — эталон.

## 7. Риски и открытые вопросы

- **Правка принципа 4.8 — решение продуктовое.** «Не показывать то, чего спека
  не обещает» противоречит тому, как сегодня объясняется выключенная передача
  у avelacom. Компромисс в 4.4 сохраняет объяснение там, где улики есть, но
  границу «что считать уликой» надо утвердить на каждое расширение до этапа 4.
- **Макеты.** Нужны: раздел «Расширения» в настройках проекта (борд 13),
  колонка/подпись стадии рядом со статусом трекера (борды 01, 02), навигация
  из трёх пунктов без «Окружения» и ветка проекта в шапке (борды 07b, 18 —
  «три состава навигации» становятся композицией).
- **Регрессия на avtoto.** После этапа 4 все привычные экраны — расширения;
  единственная защита — эталонные смоуки и тесты на трёх фикстурах. Без
  живых спек avtoto и avelacom этап 4 начинать нельзя.
- **Дрейф upstream.** Формат схемы стабилен, но `skip_specs`, хранилища,
  `initiative` — beta. Встроенная копия схемы протухает — потому предпочитать
  `schema which` при наличии CLI, и держать версию в комментарии.
- **Скиллы без команд** (`delivery: skills`): вызов по имени скилла
  `/openspec-propose`; правило дедупа это учитывает.
- **Разрешения в headless-сессии.** Скиллы upstream объявляют
  `allowed-tools: Bash(openspec:*)`; `claude -p` без `--permission-mode`
  упрётся в запрос разрешения на первом же `openspec status`. На upstream
  проявится чаще, чем на avtoto.
- **`git pull --ff-only` на каждом обновлении** для репозитория кода —
  неожиданный побочный эффект; вынести в настройку проекта.
- **Локализация по пакетам** — gen-l10n работает по пакету, но приложение
  должно собирать делегаты всех расширений; проверить на первом же пакете.
- **Что публиковать.** Расширения Redmine/GitLab/Mattermost — открывать
  (обычные интеграции). Соглашения `spec-driven-redmine` (`sprints`, форматы
  `redmine.yaml`) — решить: открытый пакет или внутренний. Архитектура
  выдерживает оба варианта, но от ответа зависит, где живут тесты на avtoto.
- **Заголовок без H1** — оставляем id.

## 8. Как перепроверить

```bash
# клон upstream рядом со Spok
git clone --depth 1 https://github.com/Fission-AI/OpenSpec.git ~/OpenSpec

# схема живёт в пакете, не в проекте
ls ~/OpenSpec/schemas/spec-driven/          # schema.yaml, templates/
ls ~/OpenSpec/openspec/schemas 2>/dev/null  # нет такого каталога
head -3 ~/OpenSpec/openspec/config.yaml

# change без стеков и без трекера
ls -a ~/OpenSpec/openspec/changes/add-change-stacking-awareness/
cat   ~/OpenSpec/openspec/changes/add-change-stacking-awareness/.openspec.yaml

# apply.tracks — кто отслеживает задачи
grep -A3 '^apply:' ~/OpenSpec/schemas/spec-driven/schema.yaml

# правила чекбоксов upstream
grep -n 'TASK_LINE_PATTERN =' ~/OpenSpec/src/utils/task-progress.ts

# имя команды во frontmatter — не вызов
grep -n "name:" ~/OpenSpec/src/core/templates/workflows/propose.ts
sed -n 1,30p ~/OpenSpec/src/core/command-generation/invocation.ts

# вложенные change'и upstream не поддерживает
sed -n 1,30p ~/OpenSpec/src/utils/nested-change.ts

# смоук Spok на upstream (после этапа 1)
SPEC_PLATFORM_DIR=~/OpenSpec dart run tool/smoke.dart
```
