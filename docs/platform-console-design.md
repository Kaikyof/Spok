# Platform Console — задание на дизайн

**Дата:** 24.08.2026 · **Макеты:** Penpot, страница «Platform Console»
**Источник требований:** `platform-console-master.md` (бизнес + техника)
**Окно:** 1280×800, минимум 1100×700 · **Тема:** тёмная · **Язык:** русский

Документ отвечает на один вопрос: **что нарисовать и в каких состояниях**.
Технические подробности сюда не вынесены — они в мастер-документе.

---

## 1. Что меняется по сути

Сегодня макеты описывают приложение для **одной** спеки (avtoto): спринты,
стеки iOS/Android, готовые сборки. Приложение становится инструментом для
**любой** спеки — и это меняет дизайн в четырёх местах:

1. **Появляется уровень проекта.** Спек много, у каждой свой клон и ключи.
   Шапка получает второй уровень, появляется мастер подключения.
2. **Структура процесса перестаёт быть постоянной.** У одной команды есть
   спринты и два стека, у другой — только мастер-спека и один стек, у третьей
   вообще плоский список. Один и тот же экран должен работать во всех вариантах.
3. **Фичи включаются и выключаются.** Нет сборок — шаг «Сборка» неактивен. Нет
   токена GitLab — блок «Код» выключен. Выключенное **не прячется, а
   объясняется**.
4. **Данные могут быть не свежими.** Статус берётся из файла мгновенно, а из
   трекера — позже. Это разные степени доверия, и они должны различаться.
5. **Пользователей трое, а экраны есть для одного.** Разработчик покрыт,
   менеджер и тестировщик — нет. Им нужны не фильтры над существующими
   таблицами, а свои экраны с другой единицей показа.
   Ролей ровно три — **разработчик, менеджер, тестировщик**; других рабочих
   мест (дизайнер, инженер эксплуатации) сейчас не проектируем, и в макетах
   их быть не должно.

## 2. Принципы, которые нельзя терять

Они заданы исходным брифом и уже отражены в бордах — при доработке сохраняются.

| Принцип | Как проявляется в макете |
|---|---|
| Состояние важнее действий | экран отвечает «где мы»; кнопки — следствие состояния, а не меню |
| Факт рядом с ярлыком | статус трекера и реальное состояние ветки видны вместе, расхождение выделено |
| Три класса действий | посмотреть · изменить локально · отправить наружу — различаются формой и весом, не только цветом |
| Предпросмотр перед отправкой | точный текст и список побочных эффектов до нажатия |
| Команда всегда видна | рядом с действием — строка, которую можно скопировать |
| Цвет не единственный носитель | состояние читается на монохромном скриншоте |
| Плотность выше красоты | инструмент открыт весь день рядом с IDE; воздух не вытесняет данные |
| Только реальные статусы | показываются статусы, существующие в трекере спеки; приложение не вводит своих категорий и оценок |
| Тема тёмная | вторая тема не проектируется |

## 3. Каркас

### 3.1. Шапка: два уровня вместо одного

Сейчас в шапке один селектор — спринт. Нужно два уровня:

```
[ Проект: avtoto-platform ⌄ ]                       обновлено 4 мин назад  ⟳
[ Спринт: Локальный вход по PIN ⌄ ]  ветка · режим сдачи · сборки
```

Подпись второго селектора **меняется по типу группировки**: «Спринт»,
«Мастер-спека», «Релиз», «Родительская задача». Нужны все варианты.

Состояния индикатора свежести: только что · N минут назад · N часов назад ·
**данные устарели** (мягкая подсветка, не блокирующая).

### 3.2. Навигация: динамический состав

Пункты появляются и исчезают в зависимости от спеки. Нужно нарисовать:

- полный состав (Спринт · Change'и · Передача · Окружение · Сессии · Документы);
- состав без «Передачи» и «Тестирования» (спека без сборок и без QA-тулчейна);
- **приглушённый пункт со счётчиком** — фича выключена, у неё N невыполненных
  требований (пункт остаётся кликабельным и ведёт на экран-диагностику).

### 3.3. Панель запуска

Уже нарисована. Добавить: **имя проекта**, в котором выполнялась команда, —
при нескольких проектах без этого непонятно, чей это лог.

## 4. Новые экраны

### 4.1. Мастер подключения проекта (борды 08–11)

Четыре шага, все видны сразу, недоступные приглушены — как в «Передаче».

**Шаг 1. Адрес.** Поле для git-URL, кнопка «Подключить», вторая ветка
«Указать локальный каталог». Подсказка о том, что нужен доступ по SSH.

**Шаг 2. Клонирование.** Прогресс с процентами или неопределённый, кнопка
«Отменить». Обязательно нарисовать **состояние ошибки** — оно частое:
нет доступа по ключу, неверный адрес, каталог занят. Текст объясняет, что
сделать, а не показывает вывод git.

**Шаг 3. Что распознано.** Ключевой экран доверия. Карточками:
тип группировки · стеки · статусы · команды · включённые фичи. У каждой —
«изменить». Внизу — сводка «распознано 5 из 6, статусы придётся указать».

**Шаг 4. Ключи.** Форма из полей, которые нужны этой спеке (состав разный!):
подпись, поле, подсказка под ним. Секреты — маскированные, с пометкой
«сохранится в связке ключей». Кнопка «Проверить» у групп (трекер, хостинг,
мессенджер) с тремя состояниями: не проверено · отвечает · ошибка.

### 4.2. Выбор существующей версии или задачи (борд 15)

**Зачем.** Версия или корневая задача может уже существовать — там уже лежит
пул задач, и команда хочет добавить туда новую фичу, а не плодить дубль корня.

**Что нарисовать** — раскрывающийся блок внутри диалогов создания:

- **чекбокс** «Добавить в существующую версию или задачу»; снят — всё как
  сейчас, корень создаётся сам;
- при включении — **список из трекера**: название, номер, счётчик задач
  («Релиз 3.7 · #63598 · 12 задач»), поиск по списку;
- **поле для URL или номера** — запасной путь, когда версии нет в списке;
  под полем — результат разбора для подтверждения («найдено: Релиз 3.7»);
- **строка в предпросмотре** перед запуском: «задачи будут созданы внутри:
  Релиз 3.7 (#63598)».

Состояния: список загружается · список пуст · трекер недоступен (тогда
доступен только ручной ввод) · введённый номер не найден.

### 4.3. Диагностика выключенной фичи (борд 12)

**Зачем.** Не прятать, а объяснять: у этой спеки нет сборок или передачи —
покажем, чего не хватает и как включить.

**Три разные причины — три разных экрана.** Это главное в разделе: «выключено»
не значит «спека кривая». Нужно нарисовать все три вида, они отличаются текстом,
кнопками и тоном.

| Вид | Когда | Заголовок | Кнопки |
|---|---|---|---|
| **Не предусмотрено спекой** | процесс команды не использует эту систему | «Эта спека не настроена на работу с MR» | Скопировать шаблон · Создать через агента · Инструкция |
| **Не настроено у меня** | спека поддерживает, но мой ключ пустой | «Чтобы видеть MR, введите свой токен GitLab» | **Заполнить** (ведёт в форму ключей к нужному полю) |
| **Не отвечает** | ключ есть, но 401 или нет сети | «GitLab отклонил ключ» / «GitLab не отвечает» | Проверить снова · Изменить ключ |

Второй вид — самый частый: новый человек в команде, спека всё поддерживает, а
ключей на его машине ещё нет. Он **не должен** выглядеть как недоделанная спека
и вести к правке общих файлов. Одна кнопка, одно поле, полминуты.

**Что нарисовать в первом виде (правка спеки):**

- заголовок фичи и одна строка «зачем она нужна»;
- **чеклист требований**: выполнено / не выполнено, у каждого — путь, где
  искали (`builds.yaml` в каталоге группы), и пометка «найдено здесь», если есть;
- три кнопки разного веса: «Скопировать шаблон» (вторичная) · «Создать через
  агента» (основная) · «Открыть инструкцию» (ссылка);
- разделение блокирующих требований и необязательных: без первых фича не
  работает вовсе, без вторых — работает частично.

**Во втором и третьем видах** чеклист не нужен: одна причина, одно действие.
Это компактный блок внутри экрана, а не отдельная страница.

### 4.4. Настройки проекта (борд 13)

То же, что шаг 3 мастера, но открывается позже: правка распознанного, роли
команд, стратегия группировки, кнопка «Перечитать спеку», удаление проекта с
предупреждением о том, что чистится клон и ключи.

**Что добавить в секцию «Роли команд».** Сейчас там четыре роли — и это верно,
но неполно: у avtoto десять команд, роли покрывают четыре. Остальные шесть
(`submit`, `reviewer`, `spec-review`, `archive`, `explore`, `redmine-push`) —
не экзотика, а ежедневная работа, и сейчас они нигде, кроме палитры.

Роль ≠ применимость:

- **роль** — какая команда получает **выделенную кнопку** (их и должно быть
  немного, иначе экран превратится в панель из десяти кнопок);
- **применимость** — где команда вообще показывается; выводится из её
  сигнатуры автоматически: `[change]` → меню карточки change'а, `[sprint]` →
  экран группы, без аргументов → общее меню.

Поэтому под таблицей ролей нужен **список всех найденных команд** с колонкой
«где показывается» и переключателем «скрыть». Так человек видит, что ни одна
команда его платформы не потерялась, и может убрать лишние.

Состояния строки: роль назначена · применимость определена по сигнатуре ·
**сигнатура не распознана** (команда только в палитре — это нормальный исход,
надо его показать).

### 4.5. Экран менеджера (борды 16–17)

**Зачем.** Менеджер смотрит редко и хочет ответ за пять секунд. Стеки, ветки и
чеклисты ему не нужны — он в них не разбирается и не должен. Плюс вторая
половина роли: он приносит ТЗ и должен запустить работу, ни разу не открыв
терминал.

**Борд 16 — «Что происходит».** Сокращённый экран, не фильтр над таблицей:

- **карточки групп**: название, одна строка состояния («готово 4 из 6»),
  индикатор блокеров; **без колонок по стекам**;
- **«Что мешает»** — блокеры человеческим языком, с именем того, кто держит:
  «Подключение биометрии — ждёт проверки на устройстве · Иван Петров»;
- на экране только **реальные статусы трекера и факты из файлов** — никаких
  придуманных категорий и оценок;
- **крупная кнопка «Новая фича из ТЗ»** — главное действие экрана.

**Борд 17 — прогресс запущенной работы.** То же, что сессия, но без техники:

- заголовок задачи и живая строка «что сейчас делает агент» — **без лога,
  без списка инструментов, без выбора модели**;
- по завершении — кнопка **«Отдать разработчикам»** (создаёт MR командой спеки);
- после неё — **ссылка на MR** с кнопкой «Скопировать», чтобы скинуть в чат.

Состояния: идёт · нужно решение человека · завершено · ошибка (с одной строкой
«что случилось» и кнопкой «Показать подробности», уводящей в обычную сессию).

Чего на этих бордах нет: стеков, веток, чеклистов, панели запуска, окружения.

### 4.6. Раздел «Тестирование» (борд 14)

Появляется, когда подключён QA-тулчейн. Список тест-кейсов: название, тип
(UI · API · E2E), признак автоматизации, связь со спекой. Плюс блок покрытия
в карточке change'а: «5 кейсов, 3 автоматизированы».

## 5. Правки существующих экранов

### 5.1. Главный экран: четыре варианта таблицы

Один и тот же экран должен работать при разной структуре процесса. Нужны
четыре состояния таблицы:

| Вариант | Как выглядит | Чей случай |
|---|---|---|
| Группа + 2 стека | текущий борд: колонки iOS / Android | avtoto |
| Группа + 1 стек | одна колонка на всю ширину, **переключатель стеков скрыт** | avelacom |
| Группа без стеков | одна колонка «Работа»: статус и задачи на уровне change'а | спека без разделения |
| Без группировки | селектор группы скрыт, заголовок «Change'и» | плоский процесс |

Дополнительно:

- **пустая группа** — не пустой экран, а объяснение и кнопка «Создать change»;
- **статус из файла против статуса из трекера** — нужен различимый признак
  (например, полая точка против залитой) и подпись под таблицей «статусы из
  файлов спеки, трекер не опрошен». Иначе устаревшее выдаётся за живое.

### 5.2. Карточка change

- **список артефактов динамический** — у разных спек он разный (`test_case.md`,
  `specs/<capability>/spec.md`); нужен вид «артефакт объявлен, но файла нет» —
  серая строка с пометкой;
- **индикатор полноты** — «3 из 5 артефактов заполнены»;
- **блок «Код» в выключенном виде** — три текста по причине (см. 4.3): спека не
  использует MR · токен не заполнен у меня (с кнопкой «Заполнить») · хостинг не
  отвечает. Плюс **ссылка «Открыть в GitLab»** даже без токена — она собирается
  из адреса и имени ветки, API для неё не нужен;
- **карточка без стеков** — один чеклист без заголовка стека;
- **меню «Ещё действия»** рядом с кнопкой «Реализовать»: все команды, применимые
  к change'у (у avtoto это ещё пять). Без него «отдать на ревью» — ежедневное
  действие — остаётся спрятанным в палитре.

### 5.3. Передача

- шаги получают **три состояния** вместо двух: активен · выполнен ·
  **недоступен с причиной** (сейчас только приглушение без объяснения);
- у недоступного шага — строка «чего не хватает и где это должно лежать»;
- вариант, когда фича недоступна целиком — ведёт на экран-диагностику (4.3).

### 5.4. Окружение

- **секции по рабочим местам** вместо одного плоского списка: спека, её
  тулчейны;
- строка «Проект · адрес · ветка» вверху;
- пометка о том, где хранятся секреты (связка ключей или файл).

### 5.5. Сессии

**Терминал — часть палитры, а не альтернатива ей.** Команда почти никогда не
запускается «как есть»: к ней дописывают словами, что именно нужно сделать.
Поэтому под палитрой живёт постоянное поле ввода:

- выбранная в палитре команда **подставляется строкой**, курсор встаёт после
  неё — дальше человек дописывает задание обычным текстом;
- **высота меняется перетаскиванием верхней границы** — свёрнут (одна строка),
  обычный (4–5 строк), развёрнут (половина экрана); выбранная высота
  запоминается;
- под полем — **три компактных селектора в одну строку: модель, уровень
  доступа и effort**; значения запоминаются по проекту, а не глобально;
- рядом — итоговая команда моноширинным, та самая, которую можно скопировать
  и выполнить руками.

Состояния поля: пусто (подсказка «выберите команду или опишите задачу») ·
команда подставлена · команда с текстом · текст без команды (свободный вопрос
агенту) · выполняется (поле заблокировано, видна кнопка «Остановить»).

- **пометка источника команды** в палитре: канон схемы · `.claude` · `Makefile`;
- **блок «следующие шаги»** после завершения — кнопки продолжения, включая
  «создать MR»; этого в макете нет вовсе, а это ключ к работе менеджера
  без терминала;
- индикатор проекта, в котором выполняется сессия;
- вид команды **без описания аргументов** — у части спек его нет.

### 5.6. Документы

- вид для мастер-спеки, лежащей одним файлом (не каталогом);
- архивные change'и с датой в имени.

## 6. Компоненты, которых не хватает

| Компонент | Назначение | Состояния |
|---|---|---|
| Селектор проекта | переключение спек | обычный · один проект (свёрнут) · загрузка |
| Чеклист требований | из чего складывается доступность фичи | выполнено · не выполнено · блокирующее |
| Индикатор свежести данных | из файла / из трекера / устарело | три вида |
| Прогресс длинной операции | клонирование, discovery | процент · неопределённый · ошибка · отмена |
| Поле секрета | ввод токенов | пустое · заполнено (маска) · проверено · ошибка проверки |
| Пункт навигации со счётчиком | выключенная фича | обычный · активный · приглушённый со счётчиком |
| Строка «создано внутри» | выбранный корень в трекере | выбрано · не выбрано |
| Карточка группы (сводка) | состояние группы для менеджера | в работе · есть блокеры · готово |
| Меню действий объекта | команды, применимые к change'у или группе | свёрнуто · раскрыто · пусто (нет применимых) |
| Строка блокера с исполнителем | что мешает и кто держит | обычный · критичный |

## 7. Состояния данных: полный набор

Проектируются все, а не только «данные загрузились».

| Состояние | Когда | Как ведёт себя экран |
|---|---|---|
| Загрузка | первое открытие, обновление | скелет с сохранением раскладки, без прыжков |
| Данные | обычная работа | плотная таблица |
| Пусто | нет группы или change'ей | объяснение и первый шаг, а не пустая рамка |
| Частичная ошибка | трекер недоступен, файлы прочитаны | показать доступное, недоступное пометить |
| Устарело | данные старше нескольких минут | мягкое напоминание, не блокирующее |
| Нет доступа | ключ не заполнен **у меня** | компактный блок «введите ключ» + кнопка в форму к нужному полю |
| Система не отвечает | ключ есть, 401 или нет сети | «отклонил ключ» / «не отвечает» + «проверить снова» |
| **Фича выключена** | **спека** не содержит нужных данных | экран-диагностика с чеклистом требований |
| **Не распознано** | discovery не понял структуру | что понял, что нет, кнопка «указать вручную» |

Последние два — новые, их в макете нет.
