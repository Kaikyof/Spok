# ADR 0001: Профиль платформы — поддержка любой спеки в Platform Console

Первый ADR инструмента, поэтому базового решения он не развивает. Контекст
процесса задаёт `avtoto-platform/decisions/0000-sdd-architecture-proposal.md`
(SDD на базе OpenSpec) — Platform Console обслуживает этот процесс, но не
принадлежит ни одной конкретной платформе.

## Контекст и проблема

Приложение выросло вокруг `avtoto-platform` и знает её конвенции наизусть:
каталоги `openspec/doc` и `openspec/changes`, имена `doc.md`, `sprint.yaml`,
`builds.yaml`, `tasks_ios.md`, `tasks_android.md`, стеки `ios`/`android`,
русские статусы Redmine, тройку Redmine + GitLab + Mattermost и команды
`/opsx-*`.

Проверка на двух других репозиториях показала, насколько это узко.

**`avelacom-platform`** — тот же каркас SDD/OpenSpec, но:

- стеки `backend`, `mobile`, `root`, `manager`, `design`; файл `tasks_backend.md`;
- мастер-спека — файл `openspec/doc/<name>.md`, а не папка `doc/<name>/doc.md`;
- спринтов нет вообще: ни `sprint.yaml`, ни `builds.yaml`, ни команды
  `/opsx-sprint`; работа идёт change'ами;
- другой набор статусов, объявленный в `openspec/redmine.yaml` (`id`, `name`,
  `closing`, `completes_task`) плюс секция `sync:` с маппингом событий на статусы;
- статус продублирован в `redmine.yaml` change'а (`status_name`, `status_id`);
- ролей нет (`AVTOTO_ROLE` и `roles:` отсутствуют), в `.env.example` только
  `REDMINE_*` — GitLab и Mattermost не используются;
- свои команды: есть `/opsx-qa`, нет `/opsx-reviewer` и `/opsx-sprint`.

Если сегодня указать приложению на avelacom, оно запустится и покажет пустоту:
ноль спринтов (в `doc/` лежат файлы, а код ищет папки), change'и без задач и
статусов (ищутся `tasks_ios.md`/`tasks_android.md`), кнопка передачи запустит
несуществующую команду.

**`webantqa/qa`** — не платформа, а инструментарий роли: спеки он не хранит, а
притягивает из платформы (`spec-fetch` клонирует `OPENSPEC_REPO` в
`workspace/openspec/`). Единица работы — тест-кейс `test_cases/<change>/test_case.md`
с frontmatter (`suite`, `automation_status`, `spec_sources`), внешняя система —
Allure TestOps, команды свои (`/qa-generate`, `/qa-md-to-allure`, `/qa-manual-run`
и ещё одиннадцать). `workspace.yaml` там нет, поэтому приложение не определит
репозиторий вовсе — а тестировщик по брифу один из трёх пользователей.

## Решение

**1. Конвенции выносятся в профиль платформы** — декларативный
`.specapp/profile.yaml`, который лежит в самой спеке и читается приложением:

```yaml
kind: platform                  # platform | role-toolkit
paths:  { sprints: openspec/doc/*, changes: openspec/changes/* }
files:  { sprint_doc: "doc.md", tasks: "tasks_{stack}.md" }
stacks: [ios, android]          # открытый список, не enum
statuses: { source: openspec/redmine.yaml }
commands: { apply: "/opsx-apply {change} --stack {stack}" }
integrations: { tracker: redmine, code: gitlab, chat: mattermost }
```

Это следует принципу самого брифа: подсказки и правила выводятся из описания
процесса, а не зашиваются в приложение — иначе разъезжаются при первой правке
процесса.

**2. Спринт — опциональная сущность.** При `sprints: none` корнем модели
становится change, а экран передачи спринта исчезает из навигации, а не ломается.

**3. Статусы читаются из репозитория, а не спрашиваются у человека.** Там, где
платформа объявляет их сама (`openspec/redmine.yaml` + `sync:`), профиль ссылается
на файл. Продублированный в change'е `status_name` позволяет показывать таблицу
без обращения к трекеру, а API оставить для свежести.

**4. Тип рабочего места — часть профиля.** `kind: role-toolkit` описывает
репозиторий роли: своя корневая сущность (тест-кейс), своя интеграция (Allure),
свои команды. Роль — это не фильтр над одной моделью, а другая модель данных.

**5. Профиль составляет агент.** Незнакомый репозиторий → сессия «просканируй
структуру и составь профиль» → экран проверки распознанного с правкой руками.
Полностью автоматически угадывать структуру нельзя: молчаливое неверное
угадывание хуже явного вопроса.

**6. Логика готовности не дублируется.** Там, где платформа или её тулчейн уже
считают готовность (`webantqa/qa: bin/change-readiness.mjs` с переопределяемым
`QA_READY_STATUS_NAMES`), приложение вызывает существующий скрипт вместо второй
реализации.

## Что изменено

- Конвенции avtoto перестают быть встроенными: пути, имена, стеки, статусы и
  вызовы команд читаются из профиля.
- `ios`/`android` заменяются открытым списком стеков (сейчас 34 вхождения в коде).
- Роли, GitLab и Mattermost становятся опциональными: состав проверок окружения
  выводится из `.env.example` конкретной платформы.
- Появляются `decisions/` и профиль как публичный контракт инструмента.

## Последствия

Хорошее: одна сборка обслуживает любую спеку; новая команда подключается
профилем, а не форком; процесс можно править, не трогая приложение.

Цена: профиль — публичный контракт, его поломка ломает всех потребителей;
добавляется слой косвенности между кодом и данными; тип `role-toolkit` требует
отдельного набора экранов, а не переиспользования существующих.

Сознательно **не** делаем сейчас: абстракцию трекера и хостинга
(`IssueTracker` / `CodeHost` / `ChatNotifier`). Она нужна только когда появится
команда не на Redmine; абстракция без второй реализации получается неправильной.
В профиль не выносится всё подряд — только то, что реально различается между
командами, иначе он станет второй документацией процесса и разъедется с ним.

## Порядок работ

1. Профиль и рефакторинг источника данных (снимает уровень «другая платформа»).
2. Мастер профиля с агентом-сканером.
3. Следующие шаги в сессиях (кнопки после выполнения, включая «создать MR»).
4. Сокращённый режим менеджера.
5. Абстракция трекера — по факту появления второй системы.
